## What Went Well

**1. One commit per story actually landed this epic — Epic 3 retro Action #2 fix worked.**

All five 4.x story commits exist with the canonical `Implement story X.Y: <title>` subject, none bundled. The epic-run skill's commit-checkpoint enforcement (commits 7f17542 and 1719e87, landed before Epic 4) drove this. Even the failure mode worked correctly: when Story 4.5's workflow path broke (see Challenge #2), Claude committed manually following the same subject convention, and the result still reads cleanly in `git log`. Compare to Epic 3 where Stories 3.3 and 3.5 had no own commits — Epic 4 has clean archaeology for every story.

**2. The pre-flight clean-tree guard introduced from Epic 3 retro saved the run.**

Attempt 2 of Story 4.1 halted because spec-fix edits from attempt 1 were uncommitted. That was the guard doing its job — without it, the workflow would have committed those edits inside Story 4.1's "Implement story 4.1" commit, polluting archaeology. The guard later needed tightening (it was over-broad on resume — see Challenge #1) but the principle was load-bearing.

**3. The full spec → spec-review → dev → code-review → adversarial-review loop caught a load-bearing bug that would have shipped.**

Story 4.5 attempt 6 code-review surfaced the high finding: `performance-card.tsx` mounted from a cold relaunch but never called `setActive(true)`. The cold-relaunch path in `main.tsx` rewrites the URL via `history.replaceState`, the route mounts — but `performanceActive` stayed `false`. Consequence: `BottomTabs` would render on the card, a 401 during boot would redirect to `/login` mid-Gig, and Wake Lock wouldn't reacquire on foreground. **AR-28 broken on every cold relaunch.** Caught by code review, fixed by adding a mount-effect that calls `setActive(true)` when `performanceActive === false`. Without the review pass this ships and Sandy hits it the first time iOS kills the app mid-set.

**4. Locked design constraint memory injection worked at the adversarial-review level.**

Sandy's locked memory `[[feedback_no_terminate_on_advance_gesture]]` was injected as a `lockedConstraints` arg to every adversarial review. Story 4.1 attempt 1 _implemented_ the last-Song inert behavior, citing the locked note as justification — but the locked note describes a _rule_, the epic split assigns the AC to Story 4.4. The reviewer caught the scope drift correctly on attempt 4. The locked-constraint mechanism functioned as designed: it didn't license over-scoping, the reviewer correctly distinguished "respect the rule" from "this story owns the AC."

**5. Sandy's production deploy worked on the first push — all 5 Epic 4 commits + sprint-status landed in one push, deploy pipeline green, smoke green.**

Compare to Epic 3 close: 16 unpushed commits at retro time, no Epic 3 commit deployed. This epic closed with commits-in-prod parity at the moment Sandy verified live. The deploy-pipeline blackout-check (Story 1.6) had no upcoming Gigs in the 24h window, so deploys ran straight through.

**6. AR-28 cleanup ordering is now explicit and tested.**

`use-performance-end.ts` documents the cleanup order: stop wake-lock retries → release sentinel → reset view → reset session pointer → `setActive(false)` **last** so all suppressions (stale-write banner, 401 hold, flusher pause) lift after lower-level cleanup. This is the right order — `setActive(false)` is the user-visible state change, and it must come after wake-lock and timers are gone, not before. The hook is covered by 6 dedicated tests.

**7. `wake-lock.ts` module-scope singleton design held under three competing callers.**

Three call-sites acquire the lock: `useStartPerformance` (entry), `useWakeLockIndicator` mount (reacquire after Resume / cold-relaunch), and the module-scope `visibilitychange → visible` listener (foreground reacquire). The module is idempotent — on success it resets `backoffAttempts` and cancels timers; on failure it accumulates backoff. The contract `acquire()` flips `performanceActive = true` itself so callers don't do a two-step dance. Backoff schedule `[0, 1000, 5000, 30000, 60000]` is unit-tested with `vi.useFakeTimers`. The `_resetForTests` export is a test-only seam (see Challenge #8 for the tradeoff).

**8. Zero new runtime dependencies across a 5-story epic. AR-46 still load-bearing.**

Wake Lock used the standard DOM `WakeLockSentinel` type (no `@types` package). Backoff was a `setTimeout` schedule, not a library. localStorage marker for OS-kill resume was 6 lines, no library. Navigate-away detection used `useLocation()` directly. The temptation to reach for a wake-lock library or a state-machine library was real — Story 4.3's chrome-visibility fix could have been XState. The team picked the minimal approach.

**9. The `useUpcomingGigs` hook + `UPCOMING_GIGS_QUERY_KEY` constant pattern wires prefetch and future consumers to the same cache slot.**

`prefetch.ts` calls `queryClient.prefetchQuery({ queryKey: UPCOMING_GIGS_QUERY_KEY, ... })`. Any future UI that mounts `useUpcomingGigs()` reads the warm cache for free. The hook itself is unmounted in V1 — but the contract is locked. Pattern works because the hook file exports the shared `UPCOMING_GIGS_QUERY_KEY` constant, not just the hook function. Same pattern would clean up future prefetch+hook pairs.

**10. The Story 4.5 24h-window self-test (`gigs.test.ts`) closed the cross-package boundary cleanly.**

The epic AC said "shared OR replicated identically with self-tests." The team chose replicate-with-self-test because `infra/` is CDK tooling and can't be imported from `api/` per the architecture boundary table. The self-test compares the inline `londonIsoDate` against the blackout-check semantics for representative BST/GMT/DST instants — so any future drift between the two implementations gets caught.

## Challenges and Lessons Learned

**1. The epic-run workflow's resume mechanics ate 5 of the 7 attempts.**

Three distinct workflow-tooling bugs surfaced during the run. None of them are story-content bugs — they're orchestration faults that consumed the bulk of the run budget.

**1a. Args double-stringification.** The `Workflow` tool's `args` parameter was passed as a JSON-encoded **string** rather than an object. In the script, `args` was a string; the fallback branch `{ epicId: args }` ran; any nested fields (`attempt`, `lockedConstraints`, `userVisiblePatterns`) were invisible. Effect: the `[attempt N]` cache-invalidation mechanism in the workflow script never worked — `attempt` always resolved to `1`, so resume calls hit cache and replayed the same halt. Claude only noticed on attempt 3 (the 9ms zero-agent replay was the giveaway).

**1b. Pre-flight clean-tree guard too strict for resume.** The Epic-3-retro guard (`commit-checkpoint guard to epic-run workflow`, commit 1719e87) didn't distinguish "prior story's uncommitted code" from "this story's in-progress spec written by attempt N-1 of create-story". Any spec-fix edit on resume tripped it. Fixed in commit c50d7d7 ("Allow current-story spec + sprint-status in epic-run pre-flight") mid-epic — the fix uses `endsWith`-based path matching to survive subagent output normalising the leading porcelain status column.

**1c. Discover-step cache invalidation on state change.** When the discover step's result changed between attempts (status went `backlog` → `ready-for-dev` in `sprint-status.yaml`), the pre-flight call _also_ re-ran live even with an unchanged prompt. The Workflow doc says "the longest unchanged prefix of agent() calls returns cached results instantly; the first edited/new call and everything after it runs live" — but in practice the cache key includes upstream state. This is load-bearing for resume mechanics and documented only loosely.

**Fix for Epic 5:** Three asks, all on the workflow harness, not the story specs:

1. Either `JSON.parse(args)` defensively when it looks like JSON, or reject string args at the tool boundary. Silent stringification of structured inputs is a serious footgun.
2. Document the cache-key behavior of `agent()` calls on resume. Currently "unchanged prefix" reads as "unchanged prompt"; the actual behavior is "unchanged prompt AND unchanged upstream state."
3. Consider a resume mode that re-runs adversarial review when code-review found high findings that were fixed in the working tree (see Challenge #2).

**2. Story 4.5 adversarial review against the final tree never ran.**

Attempt 6 halted on a code-review high finding (the `setActive(true)` mount gap). Claude fixed it in the working tree, added two regression tests, all 568 web tests + typecheck + lint green. On resume, the workflow's discover step found 4.5 status=`review` (set by `bmad-dev-story` when it finished) and **skipped** the story. The only way to re-run was to reset the status, which would have meant re-running spec-review and dev-story (cached) but the pre-flight would also halt on the now-many dirty files (more than the new c50d7d7 filter allows). Claude committed 4.5 manually using the workflow's commit-subject convention.

**The prior adversarial-review pass (against the pre-code-review tree) did run and was non-blocking — but it never saw the post-fix code.** The high-finding fix (mount-effect that flips `setActive(true)` when `performanceActive === false`) has not been adversarially reviewed against the final tree. Sandy's live verification on gig.cormie.com is the only proof that fix is correct.

**Fix for Epic 5:** Either (a) run an adversarial review on the merged Story 4.5 diff now as a one-shot, or (b) accept the risk because production smoke passed. Option (a) is low-cost — single review against the 9a1d89e commit.

**3. Architecture.md `songRefs` pseudocode is still wrong after Epic 3 retro flagged it.**

Epic 3 retro Challenge #4 flagged `generateSongId` as the naming wart that was now load-bearing in 4+ files. The rename happened in commit 5d27d6d. Good.

But the underlying architecture.md issue — the `Performance Mode entry flow` pseudocode that references nonexistent `setlist.songRefs` instead of `setlist.sections[].songs[]` — was hit again in Story 4.1 spec review (attempt 4 finding). The spec referenced the architecture pseudocode literally, the reviewer caught the schema mismatch. The Dev Notes section now carries a paragraph explaining the architecture pseudocode is stale and to use `setlist.sections.flatMap(s => s.songs)`.

**Fix for Epic 5:** Actually fix `architecture.md` around lines 643–649. One-line schema correction. Without this, every future Performance Mode story that re-reads the architecture entry-flow pseudocode hits the same trap.

**4. Locked memory-note injection has a scope-creep failure mode.**

Sandy's locked memory `[[feedback_no_terminate_on_advance_gesture]]` was passed as a constraint to every adversarial review. Story 4.1 attempt 1's spec _implemented_ the last-Song inert behavior, citing the locked note as justification. The epic explicitly assigns the last-Song AC to Story 4.4.

The reviewer caught it correctly on round 2, but the failure mode is real: a locked memory note that describes a _rule every story must respect_ can pull an implementer toward _implementing the rule in the wrong story_. Worth distinguishing:

- **Ambient rules** (every story respects): "no terminate on advance gesture," "no toasts in performance mode," "no new runtime deps." These belong as adversarial-review constraints across the board.
- **AC-owned behaviors** (one story implements): "the `NEXT ›` button is disabled on the last Song." This is one specific story's deliverable; other stories should _not_ pre-empt it even when the rule applies to their surface.

The Story 4.1 episode is the canonical worked example. The locked memory mechanism is correct; the framing in the workflow's lockedConstraints injection needs the distinction.

**Fix for Epic 5:** In the epic-run workflow's adversarial review prompt, separate the locked constraints into "ambient rules" and "story-owned ACs assigned to other stories." The first is a violation hunter; the second is a scope-creep guard.

**5. The `app-bootstrap.test.tsx:173` flake is real and reproducible.**

Confirmed at retro time: `pnpm test` from repo root fails on this single test ("expected password field to be in the document" — but the test renders the Setlists home instead). Re-running just the web package or the single test file passes immediately. The failure is in test #565 of 568 web tests, consistently the same test, consistently in the monorepo run only.

The Story 4.5 execution notes called this "intermittent flake" and noted that `main.tsx`'s new pre-mount logic (`readSessionMarker` → `history.replaceState`) only fires when `window.location.pathname === '/'` AND the marker exists — both false in jsdom. But the test does set a session marker via `localStorage.setItem` indirectly, and the bootstrap may pick it up depending on test-ordering side-effects.

This wasn't blocking — the deployed build works. But the test suite is no longer green from the monorepo root. That is a regression.

**Fix for Epic 5:** Investigate whether the new `main.tsx` pre-mount logic is the cause or whether it's pre-existing timing-sensitive code being shifted into the failure window by Story 4.5's added test cost. If the former: gate the pre-mount logic behind `import.meta.env.MODE !== 'test'`, or unconditionally clear the localStorage marker in the bootstrap test's `beforeEach`. If the latter: still worth a `beforeEach` clearing the marker — it's a cheap belt-and-suspenders.

**6. Design-note-first didn't happen for Epic 4 despite Epic 3 retro recommending it.**

Epic 3 retro flagged two candidate design-note-first artifacts: the Performance Mode entry/exit/resume state machine, and the Wake Lock backoff policy. Neither was authored ahead of Story 4.1's spec.

In practice the state machine was discovered during Story 4.3's chrome-visibility fix ("Option A vs Option B" in Dev Notes was effectively a design note inlined into a story spec). The backoff schedule was inlined into Story 4.2's Dev Notes as a `BACKOFF_MS = [0, 1000, 5000, 30000, 60000]` constant with prose justification.

Both worked. But the chrome-visibility issue specifically had a non-obvious resolution path — the `performanceView: 'card' | 'overview' | null` extension was decided inside Story 4.3 without a separate design artifact. If Sandy had wanted to revise the decision, the artifact would have been spread across the story spec rather than a standalone reviewable note.

**Lesson, not a failure:** Design-note-first is most valuable when the design space has multiple plausible options. For Performance Mode where the epic narrative already fixed the shape, inlining into the story spec was fine. For Epic 5's restore-drill runbook (Story 5.2) it will likely be valuable — there are real choices about restore boundaries, gate semantics, and operator UX. Worth authoring a `restore-drill-design.md` before Story 5.2's spec.

**7. Sandy's manual smoke pass: "UX is a mess." This is the biggest finding.**

Epic 4 delivered every AC on every story. Tests are green (modulo Challenge #5). The deploy works. Sandy can enter Performance Mode, navigate songs, exit via ×, resume from the strip, end via navigate-away, and the app survives backgrounding. Every functional requirement is met.

And the practitioner experience is poor enough that Sandy named foundational UX work as a precondition for Epic 5. Two of the execution-notes questions are now answered:

> - **How much of the "UX is a mess" reaction is per-story vs cross-cutting?** — Cross-cutting AND upstream. It's not a per-surface defect; the IA/nav/journeys layer was never specified for either surface. (Sandy 2026-06-21)
> - **Did anything from Epics 1–3 already feel wrong by the time Epic 4 exposed it?** — Yes implicitly: the same foundational gap affects every epic. Performance Mode in Epic 4 simply has the highest interaction density and the lowest tolerance for ambiguity, so the gap surfaced sharply there. (Inferred from Sandy's "back to basics for both use-cases.")

One question remains open and is gated on the IA/nav/journeys work landing:

> - Was the per-iPhone manual verification step too late in the loop to catch UX issues? Should there be a mid-epic check-in?

Note that a mid-epic UX checkpoint cannot fix a missing IA/nav/journeys layer — that gap is upstream of the epic process. Once the IA/nav/journeys artifact exists, a mid-epic checkpoint becomes a useful additional discipline, not the primary fix.

**Actual structural cause (Sandy's diagnosis, 2026-06-21):** the original design (Claude Design output, locked 2026-06-08) sketched key screens and visual direction, but never specified information architecture, navigation, or end-to-end user journeys for either desktop or mobile. Features were built screen-by-screen against AC narratives with no IA/nav/journeys backbone to align against. Local fixes accumulated — the chrome-visibility `performanceView` extension in Story 4.3, the `×`-preserves vs navigate-away-ends distinction in Story 4.4, the spatial-separation rule in UX-DR9, the locked-memory rule about advance gestures — all are patches for what should be IA-level decisions made once at the foundation layer.

The remediation is NOT more user-testing of existing surfaces. It's a foundational IA + navigation + end-to-end-journeys design pass covering both use-cases (desktop practice / mobile performance), authored before Epic 5 starts. Sandy's framing: "back to basics."

(My earlier hypothesis blamed the AC narrative being authored by a non-pianist. That was a guess that would have led to the wrong remediation. Lesson saved as [[feedback-diagnose-from-artifacts-not-personas]].)

**8. `_resetForTests` leaks test-only API into production source.**

`wake-lock.ts` is a module-scope singleton (necessary — the sentinel must survive component remount). To get deterministic test state, the module exports `_resetForTests()`. This is fine in a personal tool, but the underscore prefix isn't enforced — any production code could call it.

Lower-cost alternative: `vi.resetModules()` and re-import between tests. Slower, but cleaner. Decision deferred — `_resetForTests` works.

**Lesson, not a failure:** Module-scope singletons in TS/React are sometimes the right shape (Wake Lock is the canonical example). Where they happen, accept the testability tax. Document the contract that test-only exports are test-only.

**9. Acquire is called from three independent code paths. The contract is implicit.**

`wakeLock.acquire()` is called from (a) `useStartPerformance` on entry, (b) `useWakeLockIndicator` on mount, (c) `wake-lock.ts` module-scope `visibilitychange → visible` listener. The module is idempotent — multiple concurrent `acquire()` calls don't break — but the **intent** of each call is different:

- (a) is "the user is starting Performance Mode, the lock must be held"
- (b) is "the card just mounted (cold-relaunch or Resume), reacquire if not held"
- (c) is "the app foregrounded, reacquire if not held and we're still performing"

All three end up calling the same module function. If anyone changes the entry behavior — say, by making `useStartPerformance` _not_ acquire and deferring to `useWakeLockIndicator`'s mount — the cold-entry path silently breaks. The implicit contract is "everybody who can reacquire, reacquires; the module dedupes." That's robust today but brittle to future refactor.

**Lesson, not a failure:** Document the multi-caller contract in a `wake-lock.ts` header comment. One sentence per caller, plus the "acquire() is idempotent under concurrent callers" line.

## Key Insights

1. **The story spec → review → dev → code-review → adversarial-review pipeline justifies its cost by the Story 4.5 `setActive(true)` finding alone.** Without the code-review pass, AR-28 would have broken on every cold relaunch in production. The 7-attempt cost is real, but so is the cost of a sacred-state UI silently breaking mid-gig.

2. **Manual smoke at epic end is now the chokepoint, not story-level review.** Sandy is the only reviewer who can evaluate "feels right on stage." Five stories shipped with green code review, green adversarial review, AC-by-AC correct — and then Sandy's smoke pass surfaced "UX is a mess." The lag between code-complete and UX-verified is the whole epic. For Epic 5 (ship-gate), the UX revision _must_ happen before Story 5.2's restore-drill, not after.

3. **Workflow-tooling bugs ate more time this epic than story bugs.** Five attempts lost to args double-stringification, pre-flight overstrict, cache-key undocumented. The story content was reasonable — the orchestration harness was where the time went. Epic 5 should benefit from c50d7d7 already landing, but the other two issues are still live.

4. **`localStorage` route marker is a strictly thin shim — it works because IndexedDB already persists the data.** The TanStack Query persister (Story 2.4) is what makes cold-relaunch into Performance Mode actually feasible. The marker is 6 lines and carries only `{setlistId, songIndex}`. Without the persister underneath, AC-8 would require a full session-state serialization layer.

5. **Locked memory notes pull both ways.** They're effective at catching violations (reviewer flagged Story 4.1's last-Song over-scope correctly). They can also nudge implementers toward over-scoping (the same Story 4.1 attempt _added_ the inert behavior because the locked note was salient). The mechanism needs a "rule vs AC-owned" distinction in the prompt construction.

6. **Test growth was real but the suite is no longer monorepo-green.** +147 net tests is proportional. But `pnpm test` from the repo root fails on a single bootstrap test. That regression must close before Epic 5 — a non-green main is a discipline cliff.

7. **One commit per story works.** Five stories, five commits, clean archaeology. The Epic 3 retro Action #2 fix (epic-run commit checkpoint enforcement, commits 7f17542 + 1719e87) is the lowest-friction, highest-leverage process change of the project so far.
